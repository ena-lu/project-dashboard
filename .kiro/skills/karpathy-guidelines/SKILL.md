## 核心原則

### 1. 最簡單可行方案（Simplest Thing That Could Possibly Work）
- 優先選擇行數最少、依賴最少的實作
- 不為「未來可能的需求」預留擴充點
- 能用一個檔案解決的，不拆成多個檔案

### 2. 不增加未要求的功能（No Scope Creep）
- 嚴格對照 `requirements.md` 的使用者故事
- 未列在需求中的功能一律不實作，即使「感覺有用」
- 範圍限制欄位視為硬性禁止清單

### 3. 不建立不必要的抽象層（No Premature Abstraction）
- 不建立只被呼叫一次的函式或物件
- 不為三行以下的邏輯建立獨立模組
- 直接操作 DOM，不包裝成 helper；直接寫 CSS，不建立 utility class 系統

### 4. 每項工作都有可驗證標準（Verifiable Acceptance Criteria）
- 每次實作前，先確認對應的驗收條件（来自 `requirements.md`）
- 完成後逐條核對驗收條件，未通過不視為完成
- 驗收方式：在瀏覽器中直接開啟 HTML 檔案手動驗證

## 本專案技術約束（來自 project-rules.md）

- 純 HTML／CSS／JavaScript，無框架、無建置工具、無 Node.js
- 不呼叫外部 API，資料全部為 hardcoded mock data
- 所有網站檔案放在 `docs/` 資料夾
- 介面文字使用繁體中文
- 版面需支援響應式設計（RWD）
- 發布：GitHub Pages，Branch = `main`，Folder = `/docs`

---

## 本專案需求摘要（來自 requirements.md）

**必須實作（US-01 ～ US-07）：**
1. 顯示所有專案列表，含名稱、客戶、狀態
2. 六種狀態以不同顏色 badge 標示
3. 依客戶篩選（下拉選單）
4. 各階段預計完成日期（模擬資料）
5. 各階段實際完成日期（可輸入，不需持久化）
6. 各階段預估工時（模擬資料）＋實際工時（可輸入）
7. 自動計算並顯示工時差異，超時紅色、提早綠色

**明確禁止：**
- 登入、權限管理
- 外部 API 或後端
- 新增／刪除專案
- 圖表、統計報表
- 資料持久化

## 實作檢查流程

每次寫程式前問自己：
1. 這個函式／區塊是否對應到一條驗收條件？
2. 有沒有比現在更簡單的寫法？
3. 我是否在實作需求以外的東西？

完成後問自己：
1. 在瀏覽器直接開啟，是否每條驗收條件都通過？
2. 有沒有多餘的程式碼可以刪除？
